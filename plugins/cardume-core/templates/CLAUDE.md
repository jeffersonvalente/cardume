## Cardume

This project uses the Cardume plugins (`cardume-core` plus stack plugins). Agents, skills and
commands are discovered automatically; this section only sets the working conventions.

### Routing (automatic — the user never has to pick an agent)

- The user describes the task; you choose. Classify the level (below) first, then pick the
  specialist agent or skill whose description matches; use the `orchestrator` agent to coordinate
  multi-domain execution of an approved plan. When unsure, consult the `intelligent-routing` skill. If the user names an agent (`@backend-specialist`), use it.
- Web UI design goes through the `design-flow` skill/agent; whole websites through `site-builder`.

### Work levels (spec-driven, proportional)

Classify every request before acting, say the level in one line ("Level 2 — feature: …"), then follow it.
The user can override at any time ("just do it" → level 0/1; "full spec" → level 2/3). If two levels
are equally plausible, ask once.

| Level | Typical request | Flow (each skill defines its own artifact) |
| --- | --- | --- |
| 0 — Trivial | typo, copy change, config value, question, one-line fix | Do it; mention it in the commit message. |
| 1 — Small | bug fix or small change: up to ~5 files in one area | Mini-spec in the PR description or final report: problem, 2–3 acceptance criteria, how it was verified. A bug fix first adds a failing reproduction test, and lists the behavior that must not change. |
| 2 — Feature | new feature, or a change to more than ~5 files or more than one area | `spec` → `tasks` → `implement` → `verify` → `review` (`standards` first if `docs/standards.md` is missing). Gate optional, on request. Quick spec: if the user wants it fast, spec + tasks in one pass with one approval. |
| 3 — Product / phase | new system, new product phase, multi-team work | `prd` (product-manager) → `software-architect` writes contracts, ADRs and the feature list in `docs/prd/<slug>-architecture.md` → per feature: `spec` → `software-architect` writes tasks.md → `implement` → `verify` → `review` → `gate` (qa-gatekeeper) → user decides → release: the `release-manager` agent (or the user runs `/cardume-core:release`). |

Escalate by risk, not just size: changes touching auth/permissions, money, data migration or
deletion, public APIs/contracts, or anything irreversible are at least level 1 with a mini-spec,
and level 2 when they touch more than one file or area. If a level-1 change grows past ~5 files or
one area, stop, re-classify, and tell the user before continuing.

At every level:
- **ADRs:** when a significant technical decision is made (database, framework, library, integration
  pattern, data model, accepted trade-off), record it with the `adr` skill in `docs/adr/`.
- **Verifier independence:** whoever built something does not approve it. The `verify` skill (fresh
  context) checks a spec and owns `verify.md` and the spec's status; `qa-gatekeeper` runs gates and
  pre-merge checks against written criteria. Reports cite evidence (command + output), not claims.
- **When to involve the user:** gate decisions, changes to an approved spec/PRD/standards, decisions the
  PRD lists as blockers, and irreversible or public actions (release, tag, publish, delete, posts).
  Everything else is delegated: decide, note the reason (PR description or ADR), and continue. Batch
  open questions instead of asking one at a time.

### Code

- If `docs/standards.md` exists, it holds this project's conventions (generated by
  `/cardume-core:standards`); follow it over generic advice. Its `## Principles (manual)` section
  is set by the user and changes only with the user's approval.
- Follow the `clean-code` skill: concise, self-documenting, no over-engineering.
- Tests for logic changes (unit > integration > E2E, AAA pattern).
- Before editing a file, check what depends on it and update dependents together.
- Respond in the user's language; code, identifiers and comments in English.

### Verification

The Cardume hooks run automatically:
- after each Edit/Write, a syntax check of the changed file;
- before Claude finishes a turn with code changes, security scan + lint on the changed files
  (it blocks until they pass, up to 3 attempts);
- before destructive infra/data commands (`terraform apply`, `kubectl delete`, `bq rm`, `DROP`…),
  a confirmation prompt.

Manual checks (commands on the Bash PATH):

| Command | Purpose |
| --- | --- |
| `cardume-checklist .` | Priority audit: security → lint → schema → tests → UX → SEO |
| `cardume-checklist . --url <URL>` | Adds Lighthouse + Playwright |
| `cardume-verify-all . --url <URL>` | Full pre-deploy suite |

Checks from plugins that are not installed are skipped.

### Review and context

- Before merging non-trivial changes: `/cardume-core:review` (parallel specialist reviewers,
  verified findings only).
- Subagents return short reports; long output goes to a file under `docs/` or `.cardume/reports/`.
- Subagents cannot talk to the user: they return questions and needed approvals under
  **Open questions**. Ask the user, then resume or re-run the subagent with the answers.
